# RWB Mesh — доставка с хранением в ПВЗ

**Хакатон RWB × ПГТУ, 25–26 ноября 2026.** ПВЗ становится микро-складом ходового товара: заказ внутри зоны выдаётся с полки (**режим A**) или едет прямым рейсом ПВЗ → ПВЗ (**режим B**), минуя хаб и магистраль. Всё остальное идёт через хаб как сейчас (**режим C**). Mesh включается только там, где он выгоднее, — и каждое решение объясняется цифрами, а не чёрным ящиком.

> Все ставки и тарифы — **согласованные допущения команды**, а не тарифы RWB. Полный реестр допущений — в разделе «Допущения» ниже, в конфиге [`core/parameters.py`](core/parameters.py), на экране «Модель» и по запросу `GET /api/params`.

| --- | --- |

| Себестоимость mesh без рейса (S / M) | **50 / 80,30 ₽** |
| Экономия на заказе до рейса (S / M) | **59 / 91,70 ₽** |

## Что сделано на хакатоне

- **Полный цикл заказа**: приёмка партии → заказ → решение решателя → сборка → рейс → выдача → возврат. Через API и через интерфейс.
- **Решатель A/B/C с объяснением**: четыре фильтра (плотность зоны, габарит и место, срок, окупаемость рейса); по каждому показывается факт и лимит. Снимок решения сохраняется в заказе.
- **Ledger с двойной записью и идемпотентностью**: сумма проводок по любому заказу равна нулю; повтор запроса с тем же `Idempotency-Key` не создаёт вторых начислений.
- **Экраны**: ПВЗ (склад, приёмка, заказы, рейсы, аналитика), Продавец (полная юнит-экономика по каждому заказу), Модель (сравнение схем, порог окупаемости, чувствительность, экономика пилота).
- **Нештатные сценарии**: срыв рейса с пересчётом заказов на другой рейс или хаб; пересорт при приёмке (S↔M пересчитывается, L — отказ); неликвид — алерты на 7-й и 15-й день, блокировка пополнения и вывоз.
- **Частичная приёмка**: если партия не влезает в выбранный ПВЗ, система принимает сколько помещается, остаток раскладывает по другим точкам того же города, а неразмещённое показывает честно.
- **Прогноз спроса по SKU**: средние продажи за 30 дней × дни покрытия, минус остаток и заказы в пути; на экране ПВЗ — таблица «что завезти» с кнопкой «Завезти», для продавца — подсказка «куда везти» (топ-3 ПВЗ по спросу и свободному месту).
- **Качество**: 50 автотестов (формулы, сценарии, конкурентный резерв, идемпотентность) + сквозной браузерный сценарий. Запуск одной командой в Docker.

## Запуск в Docker

Нужны Docker и Docker Compose.

```bash
git clone https://github.com/mrFrok/rwbhak.git
cd rwbhak
cp .env.example .env
make up          # docker compose up --build -d: db + api + ui
```

- **Интерфейс**: <http://localhost:8090> (если порт занят, поменяйте `UI_PORT` в `.env`)
- **Swagger**: <http://localhost:8000/docs>

Поднимаются PostgreSQL 16, FastAPI и Nginx с собранным React. При старте API создаёт таблицы (`create_all`) и заполняет **пустую** базу демо-данными: 3 города, 12 ПВЗ (5 в Перми, 4 в Соликамске, 3 в Москве), 1 хаб-коридор, 10 продавцов, 40 SKU, 82 партии, 3 рейса (99 / 30 / 13 заказов). Повторные запуски существующую базу не трогают.

| Команда | Действие |
| --- | --- |
| `make up` / `make down` | поднять / остановить стек |
| `make logs` | логи сервиса api |
| `make seed` | заполнить пустую БД демо-данными |
| `make reset-demo` | **удалить данные демо** и вернуть исходный сценарий |
| `make test` | pytest: 50 тестов ядра и API |

## Разработка без Docker

Нужны Python 3.12+ и Node.js 22+.

```bash
make install                          # venv + pip install + npm ci
.venv/bin/python -m data.seed          # локальная SQLite, демо-данные
make test                              # 50 тестов
.venv/bin/python -m core.breakeven     # контрольные таблицы бизнес-модели
```

Два терминала:

```bash
make dev-api    # uvicorn на :8000 с автоперезагрузкой
make dev-ui     # Vite на :5173, /api проксируется на :8000
```

Интерфейс — <http://localhost:5173>. Сборка фронтенда с проверкой типов — `make build-ui`.

Браузерная проверка сквозного сценария (меняет данные демо):

```bash
.venv/bin/pip install playwright
.venv/bin/python -m playwright install chromium
.venv/bin/python tests/browser_smoke.py
```

## Демо-сценарии

На свежих данных рейс «ПВЗ Мира → ПВЗ Компрос» уже содержит 99 заказов класса S — следующий закрывает порог.

1. **Городской заказ (режим B).** **ПВЗ → Заказы → Создать заказ → Городской рейс**. Сотый заказ: **95 ₽ против 109 ₽ через хаб**, все фильтры зелёные. Соберите заказ, в **Рейсах** отправьте рейс и отметьте прибытие, выдайте заказ и откройте **Проводки** — баланс `0 ₽`. Чтобы проверить приёмку, выберите ПВЗ Мира, примите единицу S и укажите эту партию в ручной форме заказа.
2. **С полки и дальний (A и C).** В той же форме — **С полки** (52 ₽, выдача в день заказа) и **Дальний, через хаб** (фильтр расстояния не пройден — видна причина).
3. **Возврат.** У выданного заказа **Возврат → В путь → Принять возврат**: бонус за выдачу сторнируется, продавец платит обратную логистику 50 ₽, товар по возможности остаётся в ПВЗ выдачи. Три статуса имитируют обратный поток; отдельная транспортировка на хаб не моделируется.
4. **Сбой рейса.** Кнопка **Сбой** у рейса: каждый заказ пересчитывается — остаётся B, если другой рейс проходит фильтры, иначе уходит в хаб с причиной. Пересорт при приёмке: фактический класс S↔M принимается по новому тарифу, L — отказ.
5. **Неликвид.** Примите партию и жмите **+1 день**: хранение начисляется ежедневно (3 ₽/УМ-день ПВЗ, продавцу — с 4-го дня), на 7-й день появляется алерт «нет продаж», на 15-й — предупреждение о вывозе, а следующий шаг времени вывозит остаток на хаб: продавец платит 35 ₽ за единицу, место освобождается, пополнение SKU блокируется. Тариф за 14 дней (54 ₽ продавец / 42 ₽ ПВЗ за S) закрыт тестами.

Экран **Модель** считает по `analytic/` (среднее по 5 seed) те же ~2 800 заказов за 30 дней в обеих схемах: **экономия 67 607 ₽/мес (13,5%)** с попутной загрузкой; только выделенные рейсы дают 54 801 ₽/мес и не покрывают постоянные расходы пилота (−5 199 ₽/мес). Отчёт и машинные результаты — [reports/model_report.md](reports/model_report.md), `reports/results.json`; пересчёт — `make report`. Модель упрощена: срывы, возвраты и непроданный остаток потока в неё не входят.

## Допущения

Все числа — **допущения команды в разумных порядках величин**, а не тарифы RWB; они выбраны так, чтобы сравнить две схемы на одних и тех же заказах. Замена на реальные данные — правкой одного файла `core/parameters.py`, без изменения логики.

| Группа | Ключевые значения |
| --- | --- |
| Хаб (S / M / L) | обработка 25 ₽ × k_оп, хранение 3 ₽ × УМ × 3 дня, плечи 40 ₽ и 35 ₽ × k_тр → **109 / 172 / 304,50 ₽** |
| Выплаты ПВЗ | приёмка 10 ₽, хранение 3 ₽/УМ-день (с 1-го дня), сборка 21 ₽, бонус SLA +10%, бонус полки +5% |
| Рейсы | выделенный 4 500 ₽ (240 км × 12 ₽ + 6 ч × 270 ₽), попутный 750 ₽, вместимость 300 УМ |
| Габариты | S = 1 УМ, M = 3 УМ, L = 8 УМ; k_оп 1,0 / 1,3 / 1,8; k_тр 1,0 / 1,5 / 2,5; L и КГТ — только хаб |
| Площадь | ёмкость 200 УМ, резерв 15% (доступно 170), квота M ≤ 50% |
| Сроки | хаб 48 ч, mesh — ожидание рейса + 5 ч, полка ≤ 4 ч |
| Зоны | GREEN λ ≥ 38 заказов/день, YELLOW 7–38 (только попутные), RED < 7 — хаб |
| Продавец | комиссия 15%, логистика 60 ₽ × коэффициент перевозки, обратная логистика 50 ₽ |
| Хранение продавца | дни 1–3 бесплатно, 4–7 — 3 ₽, 8–14 — 6 ₽, 15+ — 10 ₽/УМ-день + вывоз 35 ₽ |
| Поток пилота | 70% S + 30% M, 4 рейса в неделю (17,32/мес), возвраты 5% |

Полные таблицы с выводом каждой цифры — в [бизнес-модели v0.3](docs/business-model.md); машиночитаемый реестр — `GET /api/params` и `core/parameters.py`.

## Архитектура и структура

| Слой | Технологии | Ответственность |
| --- | --- | --- |
| `core/` | Python, `Decimal` | Формулы, решатель, проводки, симулятор. Не знает про БД и UI |
| `api/` | FastAPI, SQLAlchemy, PostgreSQL | Транзакции, идемпотентность, остатки и брони мест |
| `ui/` | React, TypeScript, Ant Design, Recharts | Экраны ПВЗ, Продавца и Модели |
| `data/` | — | Воспроизводимые демо-данные, `seed=42`, без персональных данных |
| `tests/` | pytest | Формулы, сценарии через API, конкурентный резерв |

```
core/                  расчётное ядро: parameters, economics, solver, ledger, simulation, breakeven
api/                   models (SQLAlchemy), routers, services (orders, trips, analytics, clock)
ui/src/                App (роутер), api/ (клиент и хуки), pages/ (Pvz, Seller, Model), components/
data/seed.py           генератор демо-данных
docker-compose.yml     db + api + ui
```

Принцип **«одна формула — один код»**: интерфейс, Swagger и тесты считают деньги одними и теми же функциями `core/`, поэтому числа везде совпадают. Деньги хранятся в копейках, расчёты — `Decimal` (half-up в одном месте). Остатки ведутся с двумя полями (физический и свободный резерв) и CHECK-ограничением в БД; при резервировании строка партии блокируется `FOR UPDATE`. Время демо — модельные часы (`POST /api/time/advance`), а не реальные: хранение и алерты считаются от них.

## API

Полная спецификация — Swagger: <http://localhost:8000/docs>. Изменяющие запросы требуют заголовок `Idempotency-Key`.

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/batches` | приёмка партии в ПВЗ (с проверкой места и класса) |
| `GET /api/pvz/{id}/stock` · `/alerts` · `/batches` | остатки, УМ, алерты неликвида |
| `POST /api/orders` | создание заказа: решатель возвращает режим, стоимость и фильтры |
| `GET /api/orders` · `GET /api/orders/{id}` | список и состояние заказа |
| `POST /api/orders/{id}/pick` · `/issue` · `/return` · `/return/transit` · `/return/accept` | сборка, выдача, возврат в три статуса |
| `GET /api/orders/{id}/ledger` | проводки заказа и баланс |
| `POST /api/trips/plan` · `/{id}/depart` · `/arrive` · `/fail` | планирование и жизненный цикл рейса, сбой с пересчётом |
| `GET /api/analytics/pvz/{id}` · `/analytics/seller/{id}` | вклад ПВЗ и маржа продавца |
| `GET /api/compare` · `POST /api/simulate` · `GET /api/threshold` | сравнение схем, чувствительность, порог |
| `GET /api/params` | реестр допущений |
| `POST /api/time/advance` | модельные часы |

## Границы применимости

Mesh работает не везде: зона GREEN или YELLOW, классы S и M, ближнее плечо до 300 км. Дальше, крупнее и реже — хаб, и система сама это показывает. Симулятор упрощён: он не моделирует календарь рейсов, срывы и непроданные остатки потока и **не заявляет** достижение целевых −5% по пилоту — это цель проверки, а не обещание.

Не реализовано (осознанные упрощения MVP): платёжный шлюз, клиентское приложение покупателя, управление хабом, магистраль (заглушка `TRUNK_STUB_COST`), автоматический пересчёт зон по истории. Вывоз неликвида моделируется списанием остатка на хаб со списанием 35 ₽/единицу; обратный приём на хаб и повторная постановка на полку не моделируются.

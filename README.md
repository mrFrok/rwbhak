# RWB Mesh — доставка с хранением в ПВЗ

**Хакатон RWB × ПГТУ, 25–26 ноября 2026.** ПВЗ становится микро-складом ходового товара: заказ внутри зоны выдаётся с полки (**режим A**) или едет прямым рейсом ПВЗ → ПВЗ (**режим B**), минуя хаб и магистраль. Всё остальное идёт через хаб как сейчас (**режим C**). Mesh включается только там, где он выгоднее, — и каждое решение объясняется цифрами, а не чёрным ящиком.

> Все ставки и тарифы — **согласованные допущения команды**, а не тарифы RWB. Они вынесены в конфиг [`core/parameters.py`](core/parameters.py), видны в интерфейсе на экране «Модель» и по запросу `GET /api/params`.

## Ключевые числа модели

| Показатель | Значение |
| --- | --- |
| Себестоимость заказа через хаб (S / M / L) | **109 / 172 / 304,50 ₽** |
| Себестоимость mesh без рейса (S / M) | **50 / 80,30 ₽** |
| Экономия на заказе до рейса (S / M) | **59 / 91,70 ₽** |
| Заказ с полки (режим A, S) | **52 ₽** — экономия 57 ₽ без порога загрузки |
| Порог выделенного рейса | **66 заказов** (77 при 100% S) |
| Порог попутной загрузки | **11 заказов** — в 6 раз ниже |
| Вклад ПВЗ с заказа S | **+15 ₽** (+4 ₽ бонус за SLA) |
| Чистая маржа продавца (чек 1 500 ₽, S) | **+491,75 ₽** — не хуже хаба, оборот быстрее |
| Окупаемость пилота (60 000 ₽/мес пост. расходов) | от **116** заказов/рейс выделенным или **62** попутным |

Все цифры считаются кодом этого репозитория и защищены автотестами — см. раздел «Как проверить».

## Что сделано на хакатоне

- **Полный цикл заказа**: приёмка партии → заказ → решение решателя → сборка → рейс → выдача → возврат. Через API и через интерфейс.
- **Решатель A/B/C с объяснением**: четыре фильтра (плотность зоны, габарит и место, срок, окупаемость рейса); по каждому показывается факт и лимит. Снимок решения сохраняется в заказе.
- **Ledger с двойной записью и идемпотентностью**: сумма проводок по любому заказу равна нулю; повтор запроса с тем же `Idempotency-Key` не создаёт вторых начислений.
- **Экраны**: ПВЗ (склад, приёмка, заказы, рейсы, аналитика), Продавец (полная юнит-экономика по каждому заказу), Модель (сравнение схем, порог окупаемости, чувствительность, экономика пилота).
- **Нештатные сценарии**: срыв рейса с пересчётом заказов на другой рейс или хаб; пересорт при приёмке (S↔M пересчитывается, L — отказ); неликвид — алерты на 7-й и 15-й день и блокировка пополнения.
- **Качество**: 50 автотестов (формулы, сценарии, конкурентный резерв, идемпотентность) + сквозной браузерный сценарий. Запуск одной командой в Docker.

## Запуск

```bash
git clone https://github.com/mrFrok/rwbhak.git
cd rwbhak
cp .env.example .env
make up
```

- **Интерфейс**: <http://localhost:8090> (если порт занят, поменяйте `UI_PORT` в `.env`)
- **Swagger**: <http://localhost:8000/docs>

Поднимаются PostgreSQL, FastAPI и React; пустая база заполняется демо-данными автоматически. `make reset-demo` возвращает демо к исходному состоянию, `make test` — 50 тестов.

## Демо-сценарии

На свежих данных рейс «ПВЗ Мира → ПВЗ Компрос» уже содержит 99 заказов класса S — следующий закрывает порог.

1. **Городской заказ (режим B).** **ПВЗ → Заказы → Создать заказ → Городской рейс**. Сотый заказ: **95 ₽ против 109 ₽ через хаб**, все фильтры зелёные. Соберите заказ, в **Рейсах** отправьте рейс и отметьте прибытие, выдайте заказ и откройте **Проводки** — баланс `0 ₽`.
2. **С полки и дальний (A и C).** В той же форме — **С полки** (52 ₽, выдача в день заказа) и **Дальний, через хаб** (фильтр расстояния не пройден — видна причина).
3. **Возврат.** У выданного заказа **Возврат → В путь → Принять возврат**: бонус за выдачу сторнируется, продавец платит обратную логистику 50 ₽, товар возвращается на полку.
4. **Сбой рейса.** Кнопка **Сбой** у рейса: каждый заказ пересчитывается — остаётся B, если другой рейс проходит фильтры, иначе уходит в хаб с причиной.
5. **Неликвид.** Примите партию и жмите **+1 день**: на 7-й день алерт «нет продаж», на 15-й — вывоз (10 ₽/УМ-день + 35 ₽/ед.) и блокировка пополнения.

Экран **Модель** показывает то же самое на потоке из 3 000 синтетических заказов (`seed=42`): обе схемы на одних данных, пороги 66/11, чувствительность ±20%, экономика пилота.

## Как проверить цифры

```bash
make test                          # 50 тестов, включая контрольные числа
.venv/bin/python -m core.breakeven # печатает таблицы из бизнес-модели
```

Контрольные точки в тестах: затраты хаба 109/172/304,50 ₽; mesh без рейса 50/80,30 ₽; пороги 77/13 (S) и 66/11 (микс); маржа продавца 491,75 ₽; хранение 14 дней — 54 ₽ с продавца и 42 ₽ ПВЗ; сумма ledger по заказу — 0; повтор события не меняет состояние.

## Архитектура

| Слой | Технологии | Ответственность |
| --- | --- | --- |
| `core/` | Python, `Decimal` | Формулы, решатель, проводки, симулятор. Не знает про БД и UI |
| `api/` | FastAPI, SQLAlchemy, PostgreSQL | Транзакции, идемпотентность, остатки и брони мест |
| `ui/` | React, TypeScript, Ant Design, Recharts | Экраны ПВЗ, Продавца и Модели |
| `data/` | — | Воспроизводимые демо-данные, `seed=42` |
| `tests/` | pytest | Формулы, сценарии через API, конкурентный резерв |

Принцип **«одна формула — один код»**: интерфейс, Swagger и тесты считают деньги одними и теми же функциями `core/`, поэтому числа везде совпадают. Деньги хранятся в копейках, расчёты — `Decimal`. Время демо — модельные часы (`POST /api/time/advance`), а не реальные.

## Границы применимости (говорим честно)

Mesh работает не везде: зона GREEN или YELLOW, классы S и M, ближнее плечо до 300 км. Дальше, крупнее и реже — хаб, и система сама это показывает. Симулятор упрощён: он не моделирует календарь рейсов, срывы и непроданные остатки потока и **не заявляет** достижение целевых −5% по пилоту — это цель проверки, а не обещание. Не реализованы: платёжный шлюз, клиентское приложение покупателя, магистраль (заглушка), физический вывоз неликвида и ежедневное начисление на непроданный остаток.

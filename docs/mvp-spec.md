## 1. Цель и границы

**Цель.** Прототип полного цикла заказа, который на одних и тех же данных сравнивает mesh-схему
с базовой (через хаб) и показывает выгоду ПВЗ, маркетплейса и продавца, а также срок и цену
для покупателя.

**Входит в MVP:**
- приёмка партии в ПВЗ, хранение, заказ, сборка, рейс, выдача, возврат;
- решатель выбора режима A / B / C с объяснением решения;
- тарифы, расчёт стоимости хранения и логистики, начисления ПВЗ и продавцу (ledger);
- интерфейс ПВЗ и аналитика стоимости и прибыли ПВЗ;
- интерфейс продавца и аналитика стоимости и прибыли по заказу;
- сравнение схем, порог окупаемости, анализ чувствительности;
- API с описанием, модель данных, тесты, запуск в Docker.

**Не делаем (заглушки или данные):** платёжный шлюз, управление хабом, клиентское приложение
покупателя, магистральную логистику. Магистраль — параметр-заглушка `TRUNK_STUB_COST`
(допущение). Хаб — таблица с фиксированной стоимостью операций.

**Принцип:** *одна формула — один код.* Расчёты живут в чистом пакете `core/` без зависимостей
от БД и UI. Его используют и API, и симулятор, и тесты. Числа на слайдах, в документе и в
интерфейсе всегда совпадают.

## 4. Модель данных

| Таблица | Ключевые поля |
| --- | --- |
| `city` | id, name |
| `hub` | id, city_id, fixed_costs (обработка, хранение за УМ-день) |
| `pvz` | id, city_id, zone_id, capacity_um (200), reserve_pct (15), quiet_windows |
| `zone` | id, corridor, lambda_per_day, class (GREEN / YELLOW / RED) |
| `seller` | id, name |
| `sku` | id, seller_id, price, unit_cost, size_class (S/M/L/KGT), um, special (bool) |
| `batch` | id, sku_id, pvz_id, qty, qty_free, received_at, declared_class, actual_class |
| `order` | id, sku_id, buyer_pvz_id, source_batch_id, status, mode (A/B/C), eta_mesh, eta_hub, decision_json |
| `trip` | id, from_city, to_city, kind (DEDICATED / ALONG), departs_at, cost, status |
| `trip_order` | trip_id, order_id, um |
| `ledger_entry` | id, account, order_id, type, amount, idempotency_key (unique), created_at |
| `event_log` | id, event_type, payload, idempotency_key (unique), processed_at |
| `alert` | id, batch_id, type (NO_SALES_D7 / REMOVAL_D15 / CAPACITY), created_at |

**Статусы заказа:**

```
CREATED → RESERVED → PICKED → IN_TRIP → ARRIVED → ISSUED
                          ↘ (режим A) ──────────────↗
CREATED → ROUTED_HUB (режим C)
ISSUED → RETURN_REQUESTED → RETURN_IN_TRANSIT → RETURNED
любой статус до ISSUED → REROUTED (сбой) → ROUTED_HUB или IN_TRIP
```

Остатки ведутся по двум полям: **физический** (`qty`) и **резерв** (`qty − qty_free`).
Изменение статуса — только через событие, а событие идемпотентно.

## 5. Решатель маршрута

**Вход:** заказ, остатки по ПВЗ, параметры зоны, расписание рейсов, текущая загрузка рейса.

**Выход:**

```json
{
  "mode": "B",
  "eta_mesh_h": 35,
  "eta_hub_h": 48,
  "cost_mesh": 95.0,
  "cost_hub": 109.0,
  "filters": [
    {"name": "zone",  "ok": true,  "value": "GREEN"},
    {"name": "size",  "ok": true,  "value": "S"},
    {"name": "space", "ok": true,  "value": "free_um=62"},
    {"name": "time",  "ok": true,  "value": "35 <= 48"},
    {"name": "price", "ok": true,  "value": "buyer price unchanged"},
    {"name": "trip",  "ok": true,  "value": "saving 5900 >= trip_cost 4500"}
  ]
}
```

Каждое решение **объясняется списком фильтров** с цифрами. Это показывается в UI и
сохраняется в `order.decision_json`. Именно по этому виден «честный выбор», а не чёрный ящик.

**Правила** (из [раздела 3](business-model.md#3-решение-три-режима-и-четыре-фильтра)):

```
mode A: товар в buyer_pvz и qty_free > 0
mode B: distance <= 300 and zone in {GREEN, YELLOW} and size in {S, M}
        and free_um >= order_um and batch_um <= vehicle_free_um
        and eta_mesh <= eta_hub + delta_t
        and buyer_price_mesh <= buyer_price_hub
        and sum(saving_i) >= trip_cost (DEDICATED) или >= trip_inc (ALONG)
mode C: иначе
```

Зона YELLOW допускает только рейсы `ALONG`. Пересчёт зон: `λ` по скользящему окну 7 дней.
Для `ALONG` вычитаем уже занятые места. Приёмка: пакет 43 S + 19 M проходит при 100 свободных УМ и не проходит при 90; при уменьшении пакета заново считаем его экономию.
Перестроение при сбое: удалить недоступный узел или рейс, пересчитать для затронутых заказов.

## 6. Финансовая логика и ledger

**Счета:** `marketplace`, `pvz:{id}`, `seller:{id}`. Проводки двойные: сумма по заказу всегда 0.

| Событие | Проводки |
| --- | --- |
| Приёмка | marketplace → pvz: 10 ₽ × `k_оп` |
| Хранение (каждый день) | marketplace → pvz: 3 ₽ × УМ; seller → marketplace по прогрессивному тарифу с 4-го дня |
| Сборка | marketplace → pvz: 21 ₽ × `k_оп` |
| Выдача в срок | бонус ПВЗ: +10% к выплате за заказ |
| Продажа со своей полки (режим A) | бонус ПВЗ: 5% от выплат за операции |
| Штраф ПВЗ | pvz → marketplace |
| Возврат | сторно сборки, отдельная проводка за хранение возврата |

**Идемпотентность:** заголовок `Idempotency-Key` на всех изменяющих запросах, уникальный индекс
по `event_log.idempotency_key` и `ledger_entry.idempotency_key`. Повтор события возвращает
прежний результат и не создаёт новую проводку.

**Аналитика** считается из ledger и заказов, а не хранится отдельно:
В расчёте режима B бонус за срок уже включён в переменные расходы (4 ₽ для S за три дня); второй раз его не прибавляем. Завоз партии учитываем по плательщику и распределяем на проданные единицы, а при отсутствии продаж показываем убыток партии.
- ПВЗ: выручка, затраты (труд, место по допущениям), вклад, вклад на УМ-день, загрузка, динамика по дням;
- продавец: по каждому заказу цена, себестоимость, комиссия, логистика, хранение, возврат → маржа;
- маркетплейс: себестоимость заказа по схеме, экономия против хаба, нагрузка на хаб.

## 7. API

Swagger доступен на `/docs`. Минимальный набор:

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/batches` | Приёмка партии в ПВЗ (продавец, SKU, qty, заявленный класс) |
| GET | `/pvz/{id}/stock` | Остатки, занятые и свободные УМ, залежавшиеся партии |
| POST | `/orders` | Создание заказа, вызов решателя, ответ с объяснением |
| GET | `/orders/{id}` | Статус, режим, фильтры, ETA, стоимость |
| POST | `/orders/{id}/pick` | Сборка |
| POST | `/orders/{id}/issue` | Выдача |
| POST | `/orders/{id}/return` | Возврат |
| POST | `/trips/plan` | Формирование рейсов из накопленных заказов |
| POST | `/trips/{id}/depart`, `/arrive`, `/fail` | Статусы рейса, сбой |
| GET | `/analytics/pvz/{id}` | Стоимость и прибыль ПВЗ |
| GET | `/analytics/seller/{id}` | Стоимость и прибыль продавца по заказам |
| GET | `/compare` | Хаб против mesh на одном наборе заказов |
| POST | `/simulate` | Прогон с произвольными параметрами, чувствительность |
| GET | `/params` | Реестр допущений |
| POST | `/time/advance` | Перевод модельных часов (для сценария долгого хранения) |

Для демонстрации времени (хранение, рейсы) используются **модельные часы**, а не реальные.

## 9. Сценарии и приёмка

Каждый сценарий воспроизводится **тестом** и **командой в README**.

| № | Сценарий | Шаги | Ожидаемый результат (на допущениях) |
| --- | --- | --- | --- |
| 1 | **Городской заказ** | Партия S принята в ПВЗ A, заказ из ПВЗ B той же зоны GREEN, рейс собран из 100 заказов | Режим B; mesh 95 ₽ против хаба 109 ₽; ПВЗ получает 40 ₽ за приёмку, хранение 3 дня и сборку; срок не хуже 48 ч; ledger сходится в 0 |

## 10. Данные, тесты, Docker

**Синтетические данные** (`data/seed.py`, `seed = 42`, без персональных данных):

| Параметр | Значение |
| --- | --- |
| Города / хаб | 2 города на расстоянии 120 км, 1 хаб |
| ПВЗ | 4 (по 2 в городе), ёмкость 200 УМ |
| Продавцы / SKU | 10 / 40; около 70% класса S, 30% M, несколько L и КГТ для проверки правил |
| Заказы | 30 модельных дней, около 3 000 заказов, будни и выходные, вечерний пик |
| Дальние заказы | 15% в другой регион (режим C) |
| Возвраты | 5% |

Источник и допущения генератора описаны в README. Данные организаторов, если будут выданы,
подключаются через тот же формат.

**Тесты:**
- unit: формулы `core/` с контрольными числами из раздела 9;
- сценарные: 5 сценариев через API на тестовой БД;
- свойства: сумма ledger по заказу равна 0, остаток не уходит в минус, повтор события не меняет состояние.

**Запуск:**

```bash
git clone <repo> && cd rwbhak
cp .env.example .env
docker compose up --build      # db + api + ui
make seed                      # синтетические данные
make test                      # pytest
# API: http://localhost:8000/docs   UI: http://localhost:8501
```

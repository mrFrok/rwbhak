# ТЗ: Frontend

Для: frontend-разработчика и инфраструктуры · см. также [контракт API](api-contract.md), [общее ТЗ MVP](mvp-spec.md), [ТЗ backend](tz-backend.md)

## 0. Принцип работы

Интерфейс ходит в backend по HTTP **только по [контракту API](api-contract.md)**. Пока backend не готов, экраны
работают на заглушках с теми же JSON (`ui/mock/`): так вы не ждёте друг друга.

**Стек по умолчанию:** Streamlit (3 страницы), `requests`, графики через `plotly` или `altair`. Если вы сильнее в React, контракт тот же, но
Streamlit быстрее даёт рабочие формы и таблицы, а жюри оценивает не оформление, а работающие операции и аналитику.

**Три правила интерфейса:**
1. **Каждое решение объяснено.** Режим заказа (A / B / C) всегда показывается вместе со списком фильтров и цифрами (`filters[]`).
2. **Допущения видны.** Рядом с любой суммой, зависящей от тарифа, есть пометка «допущение»; на странице «Модель» открывается реестр `GET /params`.
3. **Числа не считаются на фронте.** Всё приходит из API. Исключение: форматирование (разряды, ₽, %).

## 2. F1. Каркас — ночью, ≈ 40 мин

```
ui/
├── app.py                 # точка входа, навигация и боковая панель
├── api.py                 # клиент: get/post, заголовок Idempotency-Key, обработка ошибок
├── mock/                  # JSON-заглушки по контракту
├── pages/
│   ├── 1_Модель.py
│   ├── 2_ПВЗ.py
│   └── 3_Продавец.py
├── components.py          # карточка решения, таблица фильтров, метрики
└── Dockerfile
```

- Переменная `API_URL` (по умолчанию `http://api:8000`), переключатель «заглушки / API» в боковой панели.
- Боковая панель: выбор ПВЗ / продавца, **модельные часы** (кнопки «+1 час», «+1 день» → `POST /time/advance`).
- Общая функция `format_rub(x)`: `67 607 ₽`, минус через «−».

**Приёмка:** `docker compose up` открывает `http://localhost:8501`, три страницы переключаются без ошибок.

## 3. F2. Страница «Модель» (сильнейшая часть для КТ-2)

Данные: `GET /compare`, `/model/scenarios`, `/model/sensitivity`, `/model/map`, `GET /params`.
Ничего считать не нужно: на ночь можно сделать целиком на `reports/results.json`.

| Блок | Содержание | Источник |
| --- | --- | --- |
| **Сводка** | 4 метрики: экономия, % к базе, срок ближнего заказа (ч), вклад ПВЗ на точку | `comparison.mesh_with_along` |
| **Сравнение схем** | Таблица: хаб / mesh (только выделенные) / mesh (+ попутные): себестоимость, экономия, доля mesh, срок, вклад ПВЗ | `comparison` |
| **Куда уходят заказы** | Горизонтальная диаграмма причин (воронка) | `comparison.*.funnel` |
| **Три сценария** | Переключатель «пессимистичный / базовый / оптимистичный» + столбцы | `scenarios` |
| **Чувствительность** | Tornado-диаграмма (±25%), переключатель метрики «маркетплейс / ПВЗ» | `tornado_marketplace`, `tornado_pvz` |
| **Зона взаимной выгоды** | Тепловая карта плотность × ставка ПВЗ, звезда в базовой точке, легенда из 4 цветов | `mutual_map` |
| **Симулятор** | Слайдеры: заказов в день, стоимость рейса (×), ставки ПВЗ (×), доля ближних. Кнопка «Пересчитать» → `POST /simulate`, результат рядом с базой | `/simulate` |
| **Допущения** | Таблица реестра (id, параметр, значение, единица, пояснение), поиск по строке | `/params` |

Готовые картинки для быстрого старта лежат в `reports/img/` (`comparison.png`, `funnel.png`, `scenarios.png`,
`tornado_*.png`, `mutual_map.png`): на ночь можно вывести их через `st.image`, потом заменить интерактивными графиками.

**Приёмка:** на странице видны сравнение трёх схем, tornado, карта и таблица допущений; слайдер «заказов в день» меняет результат.

## 4. F3. Страница «ПВЗ»: операции

Вверху выбор ПВЗ (`GET /pvz`). Четыре вкладки.

### 4.1. Приёмка
| Элемент | Поведение |
| --- | --- |
| Форма: продавец, SKU, количество, **заявленный класс** | `POST /batches` |
| Предпросмотр | Сколько УМ займёт партия и сколько останется свободно (до отправки) |
| Результат | Зелёная карточка «Принято», проводка начисления; при `409 CAPACITY` красная карточка «Нет места: нужно 20 УМ, свободно 12»; при `SIZE_NOT_ALLOWED` — «Класс L/КГТ идёт через хаб» |

### 4.2. Остатки и место
- Индикатор загрузки: `load_pct` (прогресс-бар), цвет по порогу: зелёный до 60%, жёлтый до 85%, красный выше.
- Метрики: ёмкость, доступно (с резервом 15%), занято, свободно.
- Таблица партий (`stock.batches`): SKU, продавец, класс, УМ, остаток, **дней хранения**. Строки с `alert` подсвечены, значок ⚠ с подписью `NO_SALES_D7` («нет продаж 7 дней») и `REMOVAL_D15` («вывоз»).

### 4.3. Заказы
- Три очереди (вкладки или фильтр): **к сборке**, **в рейсе / прибыли**, **к выдаче**; плюс «возвраты».
- Строка заказа: id, SKU, режим (цветная метка A / B / C), статус, ETA.
- Кнопки по статусу: «Собрать» (`/pick`), «Выдать» (`/issue`), «Возврат» (`/return`). Недоступные действия отключены.
- Клик по заказу открывает **карточку решения** (компонент `decision_card`): режим, `cost_mesh` против `cost_hub`, `eta_mesh_h` против `eta_hub_h`, таблица `filters` с галочками ✅ / ❌ и значениями.

### 4.4. Рейсы
- Кнопка «Сформировать рейсы» → `POST /trips/plan`. Показать каждый рейс: тип (выделенный / попутный), число заказов, УМ, стоимость, экономия, чистый результат.
- Блок «Перенаправлено в хаб» с причинами (`TRIP_NOT_PAYING`, `TIME`, `CAPACITY`, `SIZE`) человеческим языком.
- Кнопки «Отправить», «Прибыл», «Сбой» (`/depart`, `/arrive`, `/fail`); после сбоя показать таблицу пересчёта.

## 5. F4. Страница «ПВЗ»: аналитика стоимости и прибыли

Данные: `GET /analytics/pvz/{id}`.

| Блок | Содержание |
| --- | --- |
| Метрики | Выручка, затраты (труд + место), **вклад**, вклад на УМ-день, загрузка |
| График по дням | Линии «выручка» и «вклад» по `by_day` |
| Структура затрат | Столбец или пирог: труд, место |
| До / после mesh | Две колонки: «до» и «после» (`before_after`), разница выделена |
| Пояснение | Одна строка: «Вклад = выручка − труд − место. Ставки — допущения, см. страницу Модель» |

**Приёмка:** после сценария 1 на странице виден вклад ПВЗ, согласованный с контрольным числом (заказ класса S: +15 ₽).

## 6. F5. Страница «Продавец»

Вверху выбор продавца. Три вкладки.

### 6.1. Партии и остатки
Таблица: где лежит товар (ПВЗ), класс, количество, дней хранения, **стоимость хранения на сегодня** (₽) и **стоимость до ближайшей границы тарифа** (например, «через 2 дня ставка вырастет с 3 до 6 ₽»). Алерты `NO_SALES_D7` / `REMOVAL_D15` отображаются жёлтым и красным.

### 6.2. Прибыль по заказу
Данные: `GET /analytics/seller/{id}`.
- Таблица заказов: цена, себестоимость, комиссия, логистика, хранение, возврат, **маржа**.
- Выбор заказа открывает **водопад** (цена → минус по каждой статье → маржа). Для режима A / B / C показать метку режима.
- Итоги: выручка, маржа, платежи за хранение, среднее число дней хранения.
- Подпись: «В первые 3 дня хранение бесплатно; дальше прогрессивный тариф».

### 6.3. Тарифы
Статическая таблица сетки хранения (дни 1–3, 4–7, 8–14, 15+) и калькулятор: «Партия N штук класса X, срок Y дней → стоимость» (простое умножение по тарифу из `/params`).

### 6.4. Подсказка «в какой ПВЗ нести» (P2)
`GET /seller/{id}/recommend-pvz`. Карточки топ-3 ПВЗ с баллом и причинами («рядом спрос», «есть место», «дёшево нести»).

## 7. F6. Демо-режим для защиты

Кнопка «Сценарий» в боковой панели запускает заранее отрепетированные последовательности через API и подсвечивает шаги:

| Кнопка | Что делает |
| --- | --- |
| Сценарий 1: городской заказ | Приёмка → заказ → решение B → рейс → выдача, шаги подсвечиваются по очереди |
| Сценарий 2: заказ в другой регион | Заказ → карточка решения: режим C, красный фильтр `distance` |
| Сценарий 5: долгое хранение | Партия → «+7 дней» → «+14 дней» → алерты и сумма хранения |
| Сброс | Возвращает демо-данные к исходному состоянию |

**Живое демо длится 2 минуты:** сценарий 1 (≈ 80 сек) + один сценарий по выбору жюри (≈ 40 сек). Всё нужное должно быть **одним кликом**: вводить данные руками на защите нельзя.

**Скрипт показа сценария 1 (2 минуты):**
1. Страница «ПВЗ» → Приёмка: принять 20 ед. S (10 сек).
2. Создать заказ из другого города → открывается карточка: **режим B, четыре зелёные галочки** (15 сек).
3. «Сформировать рейсы» → тип рейса, экономия (15 сек).
4. «Собрать» → «Отправить» → «Прибыл» → «Выдать» (20 сек).
5. Вкладка «Аналитика»: вклад ПВЗ (10 сек); страница «Продавец»: маржа по заказу (10 сек).
6. Страница «Модель»: карта взаимной выгоды и сравнение схем (20 сек).

## 8. Состояния и ошибки (обязательно)

- Загрузка: спиннер; при пустых данных — пояснение «партий нет, примите партию», а не пустой экран.
- Ошибки API показываются человеческим текстом: `CAPACITY` → «Нет места в подсобке», `BAD_TRANSITION` → «Это действие сейчас недоступно», `SIZE_NOT_ALLOWED` → «Такой габарит идёт через хаб».
- Идемпотентность: повторный клик по кнопке не создаёт дубля (генерировать `Idempotency-Key` один раз на действие).
- Любое действие обновляет связанные данные (остатки, очередь, аналитику) без ручной перезагрузки.

## 9. Приёмка по экранам (чек-лист)

- [ ] `docker compose up` поднимает `ui`, страницы открываются.
- [ ] «Модель»: сравнение трёх схем, tornado, карта, три сценария, симулятор, реестр допущений.
- [ ] «ПВЗ»: приёмка с контролем места, остатки с алертами, очередь заказов с кнопками, рейсы, аналитика.
- [ ] «Продавец»: остатки с ценой хранения, прибыль по заказу, тарифы.
- [ ] Карточка решения показывает режим и все фильтры с цифрами.
- [ ] Демо сценария 1 проходит одним кликом за ≤ 80 секунд.
- [ ] Нет персональных данных и секретов.
- [ ] Все суммы помечены как допущения, не как тарифы RWB.

## 11. Что должен уметь объяснить каждый

Жюри спросит любого о его вкладе. Frontend должен уметь рассказать: откуда берутся числа на экране (API → `core/`), что означают цвета режимов и фильтры в карточке решения, почему важно показывать объяснение решения, как работает идемпотентность кнопок.
